# 原 ELF Gold 轨迹：生成、测试、校验与 GitHub 归档说明

> **适用范围。** 本说明面向 `DynamicPackage` 的离线行为等价重建。gold 是原 ELF 在精确定义输入下的字节级参考轨迹，不是编译产物，也不应用于飞行、控制、实体执行机构或安全关键用途。

## 1. Gold 是什么，为什么会很大

gold 是把原始 `DynamicPackage.elf` 视为只读标准答案后，在**固定初始条件、固定随机种子、固定设备命令、固定调用顺序和固定步数**下，逐步导出的二进制观察数据。典型的每步观察块包括：

| 观察块 | 每步大小 | 用途 |
|---|---:|---|
| CoreDynamic 调用者状态 | 264 B | 观察 33 个 `double` 状态及核心调用返回后的 ABI 行为。 |
| main telemetry | 544 B | 观察主遥测原始帧全部字节，包括 IPC 不一定承载的字段。 |
| IPC payload | 3,000 B | 观察 `sendDynTele` 对共享内存载荷的序列化结果。 |
| global `y[33]`（部分场景） | 264 B | 观察原 ELF 的全局积分状态；仅在建立该块 gold 的场景比较。 |

因此，单一 100,000 步交叉场景的 IPC gold 大小为 `100000 × 3000 = 300,000,000 B`，即约 286.10 MiB；这就是 GitHub 普通 Git 单文件限制的来源。C 源码和原 ELF 本身非常小：当前已跟踪的源码与 Makefile 合计约 564.30 KiB，原 ELF 约 112.30 KiB。

## 2. Gold 如何生成

gold **不会**在普通构建或每次回归时重新生成。它只在以下情况按独立新文件名采集：新场景首次建立金标、需要验证原 ELF 是否确定性、或为某个争议场景重新取证。

原始 `input/DynamicPackage.elf` 永远保持只读。动态采集只允许执行 `analysis/debug_runner/DynamicPackage.exec_copy`。每个 gold 场景采用以下流程：

1. 从已审阅的 GDB probe 模板复制新 probe，并使用独立的输出前缀；绝不覆盖历史 gold。
2. probe 在原 ELF 调试执行副本中建立固定初值、姿态、柔性状态、时间、轨道、随机种子、命令帧和 IPC backing。
3. probe 连续调用原 ELF 的目标入口，例如 `dyn_init`、`dyn_main` 和 `sendDynTele`，按步顺序写出观察块。
4. 对同一输入**独立运行两次**；每个观察文件使用 `cmp` 逐字节比较。只有全部一致时，才接受其中一份作为该场景的最终 gold。
5. 记录文件大小、SHA-256、probe 路径、场景合同、采集日志和原 ELF SHA-256。

H0 高偏心 50 步 re-audit 是该流程的示例：两次独立采集以及既有 gold 的 state/main/IPC/global `y` 四块均逐字节一致。详见 `high_ecc_fifty_step_delivery_reaudit_20260825.md`。

## 3. 日常测试如何使用 Gold

日常测试是**读取并比较**，不是重新采集。恢复端比较器以严格 C11 选项编译后：

1. 读取既有 gold 到内存；
2. 在相同输入合同下运行恢复 C；
3. 每一步对每个已定义观察块执行逐字节比较；
4. 报告首次差异的步号、块名、字节偏移和实际/期望字节；
5. 以非零退出码标记失败。

`make selftest` 运行全量严格门禁。针对高偏心 H0 的可单独执行入口为：

```bash
make clean && make check-h0-fifty
```

该命令不生成 gold；它读取现有 50 步 gold，并比较 50 步 × 4 个观察块。若出现报告中的第 24 或第 37 步差异，应保留终端日志、比较器路径、gold 路径和构建命令，再开始重新双采集，而不能用新运行结果覆盖 gold。

## 4. 哪些文件应当每次生成，哪些不应提交

| 文件类别 | 产生时机 | 是否每次生成 | 本地 Git 历史 | GitHub 轻量仓库 |
|---|---|---|---|---|
| `src/`、头文件、Makefile | 源码修改 | 否 | 应提交 | 应提交 |
| 原 ELF `input/DynamicPackage.elf` | 用户提供的只读基线 | 否 | 应保留 | 可提交，约 112 KiB |
| probe（`.gdb`）与比较器（`.c`） | 新测试场景 | 否 | 应提交 | 应提交 |
| 场景合同、coverage matrix、SHA-256 清单（`.md`） | 新证据或结论 | 否 | 应提交 | 应提交 |
| 小型代表性 gold | 新场景首次采集 | 否 | 可保留 | 可选提交，用于演示小场景 |
| 大型 long-horizon gold（尤其 10k/100k） | 新长时域场景首次采集 | **否** | 可保留于完整交接归档 | **不进入普通 Git** |
| `make selftest`、比较器运行日志 | 每次执行 | 是 | 仅关键最终门禁日志可保留 | 不应逐次提交 |
| `build/` | 每次构建 | 是 | 不提交 | 不提交 |

当前完整本地 Git 已跟踪约 911.19 MiB，其中 gold 二进制约 521.93 MiB、回归/采集日志约 354.33 MiB；两者合计占绝大多数。日志和原始 gold 的作用是离线可审计取证，不是每次 GitHub 协作必需的源码内容。

## 5. GitHub 轻量仓库与完整归档的推荐边界

GitHub 轻量仓库应当以代码审阅、构建说明、测试方法和场景定义为目的，建议包含：

- 所有 `src/`、头文件、Makefile 和轻量构建说明；
- 只读原 ELF；
- 所有 GDB probe、恢复端比较器、分析脚本和场景 Markdown；
- 最终 Microsoft Word/PDF 文档及其生成器；
- gold 清单、SHA-256 清单、场景矩阵、gold 采集方法和有限验证边界；
- 可选的少量 10/50/100 步代表性 gold，用于快速演示。

下列内容不应进入 GitHub 普通 Git 历史：

- 10,000/100,000 步全量 `.bin` 轨迹；
- 每次自测产生的重复大日志；
- `build/`；
- 可由完整交接包恢复的重复二进制中间产物。

完整 gold、全部历史日志和 `.git` 完整历史应继续放入带 SHA-256 的 ZIP/TAR 交接包。若要在 GitHub 提供完整资产，可作为私有 Release 附件上传完整交接 ZIP；该附件与轻量仓库分离，不受普通 Git 单文件对象限制。

## 6. 再生成与再验证原则

1. **不要为了日常测试重新生成 gold。** 日常重新生成会掩盖恢复 C 的错误，破坏原 ELF 对照的意义。
2. **只在新场景或争议复核时重采集。** 必须双采集、独立命名、`cmp`、SHA-256 和场景合同齐全。
3. **不要覆盖历史 gold。** 新证据使用新文件前缀；旧文件只读保留，直到完整性审计决定归档策略。
4. **GitHub 轻量仓库不是完整验证资产的替代品。** 它提供可审阅代码和可复现方法；完整二进制证据由版本化 ZIP/TAR 与哈希承担。
5. **全域等价不能由有限 gold 证明。** gold 只证明当前 Linux x86-64、当前运行时、当前严格构建和精确定义输入合同下的有限逐步 bitwise 一致性。

## 7. 当前 GitHub 发布前检查

在创建远程仓库前，应从本地完整工程生成一个不包含大 gold 和重复日志的轻量镜像，并在镜像中明确说明：完整验证需要下载相应的经过 SHA-256 校验的交接包。推送前还应确认：仓库为私有、仓库不含 `build/`、单文件均小于 GitHub 普通 Git 的 100 MiB 限制，并记录本地完整交接 ZIP 的文件名与 SHA-256。
